# 添加埋点

## 四条约束

1. **不能影响其他埋点。** 非目标事件的名称、参数、取值来源、触发条件、时机和次数均保持不变。给目标事件补参数时，保留原有字段与上报次数，不顺手修改旧口径。
2. **原来没有埋点的位置，要更谨慎。** 先确认该位置对应的业务动作、回调频率，以及上层调用、下层方法、代理或观察者是否已经上报。不能因为当前函数没有上报代码，就认定需要新增调用；触发时机不明确时先询问用户。
3. **优先复用通用上报方法。** 补参数应通过原有参数入口传入，由既有调用完成上报；不要为补字段新写独立上报函数，也不要紧跟原有上报再发送一次。确需新增事件时，优先使用现有通用发送入口；无法安全复用时，说明原因并做最小范围的实现。
4. **复用不能造成其他事件重复上报。** 调用前读清方法内部的全部上报与副作用，确认它只发送目标事件。不能为了复用其中一个事件，重新调用会连带上报其他事件的流程方法。

## 执行顺序

1. 列明本次目标事件、action、新增参数和预期触发次数；区分“新增事件”和“给已有事件补参数”。
2. 从业务触发点追到最终发送入口，检查通用方法及相关调用方，找到唯一合适的修改位置。
3. 只在目标场景传入新增参数。若必须修改通用方法，保证未传新参数的调用方行为完全不变；不要修改共享参数字典导致其他事件被动带上新字段。
4. 验证目标场景和至少一个共享方法的非目标场景，比较修改前后的事件序列、次数及参数。按实际链路覆盖重复回调、重试、页面再次展示等容易重复上报的情况；不要为掩盖错误调用位置而随意增加去重开关。
5. 交付时简述改了哪些埋点、复用了哪个入口，以及如何确认其他埋点不受影响。无法运行验证时，明确区分代码检查结论与尚未验证的运行时行为。
